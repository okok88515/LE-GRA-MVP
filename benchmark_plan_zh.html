BENCHMARK PLAN

把場景框架真正落地成一套可以長期沿用的 benchmark 命名與腳本分層

既然實驗場景已經升級成 `CQI dispersion × RB heterogeneity × resource pressure`， 那 benchmark 與腳本也不應該再只是隨手命名。 更好的做法是：先定義一套穩定的場景代碼，再把 benchmark 分成 showcase、core matrix、full matrix、robustness、ablation 幾個層級。這樣之後不管你是自己跑、交接給別人跑、還是要寫論文，都能快速對齊。

Naming Rule

建議採用的場景代碼

我建議之後所有 benchmark 都統一用三段式代碼： d{dispersion}_h{heterogeneity}_p{pressure}， 後面再接一個可讀名字。這樣你一眼就能知道它在場景矩陣中的位置。

`d1`：CQI 密集（dense）
`d2`：CQI 輕微分散（midspread）
`d3`：CQI 高度分散（widespread）
`h1`：RB profile aligned
`h2`：RB mildly heterogeneous
`h3`：RB strongly heterogeneous
`p1`：low pressure
`p2`：medium pressure
`p3`：high pressure
範例：
bench_d2_h2_p2_main_general
bench_d1_h3_p3_dense_hard
bench_d3_h1_p2_cqi_easy
File Naming

建議的檔名規則

腳本：run_bench_*.py
scenario spec：bench_d2_h2_p2_main_general_spec.json
bundle：bench_d2_h2_p2_main_general_bundle/
結果資料夾：bench_results/d2_h2_p2_main_general/
報告：bench_report_d2_h2_p2_main_general.html
Why This Helps

這樣命名的好處

對研究：一看就知道每個結果在矩陣哪一格。
對交接：不用靠記憶猜 `r4 / r8 / q10` 到底是哪一類場景。
對論文：很容易把 benchmark 表格、圖表與 appendix 對齊。
對未來擴充：之後新增 radio-aware 或 trace-driven 版本，也能在同一規則下延伸。
Scripts

建議的腳本分層

不要再讓一支腳本同時扮演「找場景、訓練 learner、做 robustness、產出總報告」四種角色。 比較穩定的做法是拆成下面六種。

run_bench_showcase_suite.py 只跑 5 個代表場景，給論文主文與快速 sanity check 用。
run_bench_core_matrix.py 跑縮減版矩陣，通常是 9 格，用來驗證場景框架是否成立。
run_bench_full_matrix.py 真正跑完整 `3 × 3 × 3 = 27` 格，只在主結論穩了之後再做。
run_bench_seed_robustness.py 對少數關鍵 benchmark 做 seed sweep，確認不是單一 seed 巧合。
run_bench_feature_ablation.py 固定 benchmark，只比較 `CQI / resource-cost / multi-feature / learner`。
build_bench_report.py 把所有 csv 匯總成統一圖表與 HTML 報告。
Benchmarks

建議先定義的 benchmark 組合

先不要一開始就全鋪。最實際的做法是先有三個層次： `showcase 5 格`、`core matrix 9 格`、`full matrix 27 格`。

Showcase Suite（5 格） 給主文、proposal、口頭報告、快速驗證用。 
bench_d3_h1_p2_cqi_easy
bench_d2_h2_p2_main_general
bench_d1_h3_p3_dense_hard
bench_d2_h3_p3_main_hard
bench_d1_h1_p1_control_easy
Core Matrix（9 格） 固定 `pressure = p2` 與 `p3` 的重點區域，先驗證三軸框架。 
bench_d1_h1_p2
bench_d1_h2_p2
bench_d1_h3_p3
bench_d2_h1_p2
bench_d2_h2_p2
bench_d2_h3_p3
bench_d3_h1_p2
bench_d3_h2_p2
bench_d3_h3_p3
Full Matrix（27 格） 完整鋪開所有 `d1~d3 × h1~h3 × p1~p3`，適合最後做總表與 appendix。
Recommended Order

建議實際執行順序

第 1 步：先跑 run_bench_showcase_suite.py，確認敘事是否成立。
第 2 步：如果 showcase 有區分度，再跑 run_bench_core_matrix.py。
第 3 步：挑 2~3 個最關鍵 benchmark 做 seed_robustness。
第 4 步：最後才考慮 full matrix 與完整 appendix。

Directory Layout

建議的輸出資料夾結構

bench_results/
  showcase/
    bench_d3_h1_p2_cqi_easy/
    bench_d2_h2_p2_main_general/
    bench_d1_h3_p3_dense_hard/
  core_matrix/
    bench_d1_h1_p2/
    bench_d1_h2_p2/
    ...
  robustness/
    bench_d2_h2_p2_main_general_seed_sweep/
  ablation/
    bench_d2_h3_p3_main_hard_feature_ablation/
  reports/
    showcase_report.html
    core_matrix_report.html
這樣未來你在看結果時，不會再出現「這個 csv 到底是哪次實驗跑出來的」的問題。 也更適合之後 push 到 GitHub、做交接、或整理論文附錄。
Bottom Line

一句話總結

之後的 benchmark 應該從「隨著研究過程長出來的個別 family 名稱」， 轉成「由場景框架主導的正式 benchmark 系統」。 我會建議你正式收斂成： 三段式場景代碼 + 六類腳本分工 + 5/9/27 三層 benchmark 組合。 這樣你接下來的每一次實驗，不只是在跑結果，也是在累積一套可解釋、可交接、可寫進論文的方法論。
