面向 CQI 感知多播分組的候選聯集 K-means 框架

在已發表的單一特徵 CQI k-means 分組方法基礎上，擴充獨立產生的候選家族，並以資源塊預算下的精確效用評分選出最佳解。

摘要

多播影音傳輸讓多個使用者共享同一份無線資源，服務品質受限於群組中訊號最差的成員。單純以 CQI（Channel Quality Indicator，通道品質指標）分組是一個很強的 baseline，但可證明對兩種結構性損失視而不見：CQI 對應速率的非線性，以及單一寬頻數值看不到的頻域選擇性差異。 本方法保留 CQI k-means 作為基礎，但把分組問題重新表述成一個 候選聯集（candidate union）：各自運算成本低廉的分割式啟發法，各自針對每個群組數 k = 1…K 提出一組分組方案，每個方案都用同一套精確動態規劃資源分配器評分， 取分數最高者。因為評分是精確且共用的，加入一個候選家族可證明絕不會比不加入更差——但這個保證本身沒有告訴你一個家族實際貢獻了多少， 所以最終方法不是靠這個保證本身決定的，而是透過完整的冪集（power-set）消融實驗決定：把三個候選特徵家族的 全部 7 種非空組合，逐一拿去和單純 CQI 比較，測試場景是真實 OMNeT++/Simu5G 物理層模擬。其中兩個家族——資源成本， 以及成對精確效用遺憾（regret）圖——各自都帶來真實、穩定的增益（單獨的 regret-graph：在 120 個 confirmatory 測試案例中零敗場）；第三個家族，切換狀態感知，在各項指標上都持續明顯偏小，不論和哪個家族組合都一樣， 因此在這個量化基礎上被排除於最終方法之外。最終的兩家族聯集，其主導機制自身的效果， 在真實資料使用者規模從 24 人擴大到 40 人時不減反增。

1 問題形式化

一個基地台服務 n 個影音多播使用者，共有 R 個資源塊（resource block，RB），其中 Ravail ≤ R 是本次配置週期分配給此服務的預算。每個使用者 u 針對每個頻帶 b 回報其可達成速率 ru,b， 由回報的 CQI 推算而來。影片提供六種離散位元率之一：

B = {200, 550, 1500, 3000, 5800, 7500} kbps，
(1)

索引 q = 0…5。使用者被分割成互不相交的多播群組 G1, …, GM； 由於多播傳輸受限於訊號最差的接收端，一個群組在頻帶 b 上的可達速率為：

rG,b = minu∈G ru,b 。
(2)

給定一個群組的速率剖面，達成目標位元率所需的最少 RB 數，是把該群組自己的頻帶依速率由強到弱貪婪消耗、 直到累積速率達標為止，可精確計算：

c(G, q) = min { m : ∑i=1m r↓G,i ≥ B[q] }，
(3)

其中 r↓ 代表群組各頻帶速率由大到小排序； 若即使用滿所有頻帶也無法達標，則 c(G,q) = ∞。分組問題即為：選擇一種分割方式與每個群組的畫質指派 qG ∈ {−1, 0, …, 5} （−1 代表未服務），在滿足 ∑G c(G, qG) ≤ Ravail 的前提下，最大化總效用。

2 效用函數

每個被服務的使用者貢獻一個正規化到 [0,1] 的 log-bitrate QoE 分數：

s(q) = ln B[q] − ln B[0] ln B[5] − ln B[0] ，
(4)

並針對使用者前一個畫質等級 qprev， 以權重 β 懲罰切換行為。一個群組在畫質 q 下的貢獻為：

v(G, q) = ∑u∈G s(q) − β |q − qprev,u| 5 ，
(5)

若未服務則為 −2|G|。整體效用是所選群組各自貢獻值的每人平均， 也是後面每一個候選分組方案最終被評判的依據。

3 精確資源分配

給定一個固定的分割方式，選擇每個群組的畫質等級是一個 multiple-choice knapsack （多選背包）問題：每個群組是一個 item class，每個畫質等級（或未服務）是一個互斥選項， 成本為 c(G,q)、 價值為 v(G,q)， 容量為 Ravail。以動態規劃在累積 RB 用量上精確求解：

1狀態：dp[u] = 恰好使用 u 個 RB 時能達到的最佳總價值 2dp[0] ← 0 3對分割方式中每個群組 G： 4 對 G 每個可行的 (畫質, 成本) 選項： 5 dp[u + 成本] ← max(dp[u + 成本], dp[u] + v(G, 畫質)) 6回傳 dp[u] 在 u ≤ R_avail 範圍內的最大值

這是唯一對一個分組方案評分的地方，而且是精確的——不是代理指標，也不是貪婪捷思法。 本方法中任何地方考慮的每一個候選分割方式，都是用這同一套 DP 評分。

4 候選聯集架構

直接找出效用最大化的分割方式，是一個組合最佳化的集合分割問題。本方法不直接搜尋這個空間， 而是從幾個運算成本低廉、結構上彼此不同的啟發法（稱為「家族」）各自收集候選方案， 用上述 DP 精確評分，保留最佳者：

  1. 每個家族 f，針對每個群組數 k = 1…K， 各提出一個分割方案——每個家族貢獻 K 個候選方案。
  2. 所有家族的候選方案匯總、去除重複。
  3. 每個獨立的候選方案都用精確 DP（第 3 節）評分。
  4. 回傳分數最高的候選方案。
命題。 因為每個候選方案都用同一個精確函式評分，候選集合中的最佳分數只會隨著加入更多家族而提升，不會下降。 因此在單一決策時刻，加入一個家族保證是弱優勢（weakly dominant）的：它不可能讓選出的分組變差， 只可能在真的出現更好的選項時改變結果。

這個保證只在單一決策時刻成立。在一連串時序決策中，被選出的分組會改變每個使用者的狀態 （qprev），進而影響「下一次」決策——擁有不同候選集合的兩個方法， 可能因此走上不同的軌跡，所以這個保證不會延伸到整條軌跡的累積效用，只保證每一個獨立步驟。 第 7 節會報告這件事在實務上何時真正有影響。

5 候選家族

家族一

CQI k-means

在每個使用者目前的寬頻 CQI 上做一維 k-means。這是 baseline：運算快，且當 CQI 本身就能良好預測 RB 可行性時，這個方法就是正確的。

家族二

資源成本 k-means（Resource-cost k-means）

在一個六維的 per-user 向量 cu = ( c(u,0), …, c(u,5) ) 上做 k-means，用公式 (3) 計算，把 u 當作自己群組裡唯一的成員。 兩個寬頻 CQI 完全相同的使用者，如果各自頻帶的剖面形狀不同，所需的 RB 數可能差很多—— 這個特徵是家族一看不到、這裡才看得到的。

家族三

精確 regret 譜分群（Exact-regret spectral graph）

不是 k-means：一個成對親和圖（pairwise affinity graph），用譜嵌入（spectral embedding）分群。 對每個使用者 i、以及每一對 (i,j)， 在一個「獨佔預算」（exclusive-budget）近似下計算單獨能達到的最佳價值——彷彿該使用者或該對使用者 獨佔了完整的 RB 預算，藉此避免對每一對都重複求解真正共享預算的 DP、造成 n2 倍的運算量：

regret(i,j) = vsolo(i) + vsolo(j) − vpair(i,j)
(6)

轉換成親和度 wij = exp(−regret / scale)， scale 為所有正值 regret 的中位數。譜分群透過未正規化圖拉普拉斯矩陣 L = D − W 最小的 k 個特徵向量嵌入使用者，再對嵌入結果做 k-means。 這個家族直接量測「把兩個使用者強制分在一起的真實代價」，而不是用一個代理距離——這很重要， 因為 CQI 對速率的映射在低端有很陡的非線性：兩個使用者數值上很小的 CQI 差距， 可能隱藏著很大的 RB 可行性斷崖，這是家族一與家族二的線性距離分群天生看不到的。

還有第四個候選——切換狀態感知，在聯合座標（CQI、前一個畫質等級）上做 k-means—— 同樣被實作出來，並透過第 7 節的完整冪集消融測試過。結果顯示不論和哪些家族組合， 它在各項指標上的貢獻都明顯小於家族二與家族三，因此在這個量化基礎上被排除於最終方法之外， 而不是憑假設排除。

6 最終方法

已驗證的方法把三個家族聯集起來，用精確 DP 分數挑選：

1函式 分組(scenario, K, beta)： 2 候選方案 ← [] 3 候選方案 += CQI_kmeans(scenario.cqi, K) 4 候選方案 += 成本_kmeans(resource_cost(scenario), K) 5 候選方案 += 譜分群(regret_affinity(scenario, beta), K) 6 回傳 unique(候選方案) 中 exact_DP_utility(·, scenario, beta) 最大者

群組數在每個家族內部都掃過 1…K（已驗證設定中 K=3）；k-means 每次呼叫用 10 次隨機重啟。先前上線的版本曾額外包含切換狀態感知； 第 7 節報告移除它背後的完整消融結果。

7 實證驗證

在真實的 OMNeT++ 6.3 / INET 4.6 / Simu5G 1.4 / Veins 5.3 物理層模擬上評估， 搭配 SUMO 產生的車輛移動軌跡（不是合成 CQI 產生器）——兩個 gNB，per-band CQI 回報直接從模擬器記錄， 含真實的 handover 與排程動態。

規模泛化：留下來的機制效果不減反增

最終的兩家族方法，在一個獨立產生的真實資料場景上重新評估，使用者數 n=40 （從 n=24 提高），是目前這套模擬 pipeline 能穩定支援的最大規模。 家族三自身的貢獻——透過跟「只有資源成本」的方法比較來衡量——在使用者規模變大時效果更大， 在它鎖定的資源稀缺情境下最明顯：

8 複雜度

每次分配時刻，有兩塊運算：精確 DP 評分（每個獨立候選方案跑一次）， 以及家族三的候選產生（跑一次，K 個群組數共用）。這兩塊的成長方式並不一樣， 而主導項也不是單純看漸進複雜度會以為的那一個。

DP 資源分配：便宜，而且比公式暗示的還便宜

allocate_and_evaluate 是一個 multiple-choice knapsack： 對每個群組（共 M 個），對每個可達到的 RB 用量狀態 （最多 Ravail+1 個），對每個畫質選項 （|B| = 6 個），都會呼叫一次 value_fn 並疊代最佳解。慣常的寫法會把每個候選方案的成本上界寫成 O(M · Ravail · |B|)——但 value_fn 本身要花 O(|group|)， 而且它不依賴正在被疊代進去的 RB 用量狀態，所以在每個能到達某個群組的最多 Ravail+1 個狀態裡，都被一模一樣地重新計算了一次。 把所有群組加總（M 個群組把全部 n 個使用者分割掉），更精確的上界其實是 O(n · Ravail)——這是一個真實、但不算大的低效率： 只要把價值計算搬到 RB 用量迴圈外面，就能把 Ravail 這個因子完全去掉。用真實資料實測，這一切在絕對時間上都不重要：

成本真正在哪裡——以及一個修正

家族三有兩個子步驟：建構 O(n2) 的 pairwise regret matrix（pairwise_exact_regret_matrix），然後透過拉普拉斯矩陣最小的 k 個特徵向量做嵌入（稠密特徵分解為 O(n3)），對每個 k = 1…K 各跑一次。這份文件先前的版本寫「使用者數較大時特徵分解的運算量會主導整體成本」， 這個判斷單純是從漸進複雜度的階數推論出來的。實際量測結果卻推翻了它：

結果——上面那個複雜度說法是錯的

在 n=288 時，regret-matrix 的構建比原本以為會主導成本的特徵分解慢了 77 倍。原因是實作方式，不是漸進複雜度本身：pairwise_exact_regret_matrix 是一個沒有向量化的 Python 雙層迴圈，逐對呼叫函式，跑過 n²/2 組配對；而 np.linalg.eigh 則是單一次向量化的 LAPACK 呼叫。在這個 pipeline 目前支援的任何規模下， 帶有巨大單次運算常數的 O(n2)， 都贏過用最佳化數值程式碼跑的 O(n3)—— 特徵分解的較差階數理應反超的交叉點還沒被測到，需要比這裡測試過的規模大得多的 n 才會出現。

在 MBS 規模下的意義

MBS 本來就是明確的多使用者情境——一個群組是數百到數千個接收端，不是目前驗證過的幾十個。 另外用 n=504 和 n=816 兩個真實資料點， 把 regret-matrix 構建的成長乾淨地擬合成 build(n) ≈ 0.02566 · n2 ms（只用 n=816 這個點 去預測 n=504 的結果，誤差只有 0.4%）；特徵分解在這個範圍內 一直比它小兩個數量級，不是限制所在。把這條擬合公式反過來用，對每一個重新分組的延遲預算， 可以算出目前這個未向量化的實作最多能撐到多大的 n：

誠實的限制

照這個方法實際驗證過的節奏來看，目前的實作大概只能支援 n ≈ 200—— 比 MBS 數千使用者的目標整整差了一個數量級。就算把重新分組間隔放寬到需要另外論證合理性的程度 （對應第 7 節討論過的「把分組節奏跟每次 DP 分配節奏拆開」），天花板也只能到幾千， 而且那是在 5 分鐘這種對大多數部署都不切實際的節奏下才到得了。這不是單靠漸進複雜度分析就能發現的， 必須實際量測這個實作才會浮現。從這個診斷可以直接推出兩個具體、但目前都還沒做的修正： 把 pairwise_exact_regret_matrix 用 numpy broadcasting 向量化，取代現在的 Python 雙層迴圈（單這一步的常數因子有機會降低 100–1000 倍——大致就是目前測到的 200 人天花板跟 MBS 數千人目標之間的差距）；以及把稠密特徵分解換成只取需要的特徵向量的 稀疏/截斷解法（eigsh），並且先把目前全連通的 affinity graph 稀疏化成 k-nearest-neighbor graph。這兩者都還沒實作、沒驗證；在 MBS 規模下，候選聯集架構本身提供的 退路——拿掉家族三，只保留兩個 O(n) 的家族——是今天就能用的誠實部署選項， 代價已經在第 7 節被精確量化，不是空談。

9 未來方向：向量化與 kNN 稀疏化

第 8 節已經追出家族三真正的成本來源，是沒有向量化的 O(n2) Python 迴圈，不是特徵分解， 也量化出目前的天花板（在驗證過的 1 秒節奏下 ≈ 200 人）。 從這個診斷可以直接推出兩個具體的修正方向——但它們買到的東西不一樣， 只有其中一個是「免費的午餐」。

向量化：同樣的計算，更小的常數

把 pairwise_exact_regret_matrix 裡的雙層 Python 迴圈換成 numpy broadcasting——把 best_solo_value 對所有配對一次算完，用向量化的陣列運算 取代 n²/2 次個別的 Python 函式呼叫——是這類效能問題的標準解法， 通常能拿到 100–1000 倍的常數因子改善，而且完全不改變計算內容：算的還是每一對的精確 regret。把這個倍率套進第 8 節擬合出的成本公式（build(n) ≈ 0.02566 · n2 ms），可以把 1 秒天花板從 n≈200 推到大約 n≈2,000–6,000—— 已經涵蓋 MBS 目標範圍的大部分，而且因為演算法本身完全沒變，Section 7 的所有 confirmatory 結果跟精確性保證都完全不受影響。老實的限制是：這只是把牆推遠，不是把牆拆掉。 計算本身還是 O(n2)；n 夠大的時候，同樣的天花板還是會出現，只是出現得比較晚。這是風險最低、報酬最高的第一步， 也是應該排在下面那一步之前先做的事。

kNN 稀疏化：一個不同的演算法，需要自己的驗證

要拿到漸進上更好的階數，前提是一開始就不去對所有 n²/2 組配對都算精確 regret。標準做法是：先用一個便宜的 proxy 距離——家族一、二本來就有的 CQI 或 resource-cost 特徵向量——透過 KD-tree 或 ball-tree 找出每個使用者的 k 個最近鄰居（建樹成本 O(n log n)，查詢加總成本 O(n log n)），然後只對這 O(n·k) 組候選配對去算真正的精確 regret；不在候選鄰居範圍內的配對， 直接給 affinity 0，不再評估。搭配稀疏圖之後，特徵分解也可以從稠密的 np.linalg.eigh 換成迭代解法（eigsh，基於 Lanczos）， 每次迭代成本是 O(nnz) = O(n·k)， 跑在現在已經稀疏化的拉普拉斯矩陣上。

這不只是「同一件事的更快版本」

把精確 regret 的評估範圍限縮在 proxy 距離定義的鄰域內，等於假設「proxy 距離判定為遠」的配對， 真正的 regret 也一定不重要。第 5 節本身就是在警告這個假設可能不成立：兩個寬頻 CQI 完全相同的 使用者，per-band 的 RB 成本剖面仍然可能差很多——這正是家族二跟精確 regret 公式存在的理由，而不是單純依賴 CQI 距離就夠。用 CQI-only 或 resource-cost-only 的 proxy 建出來的 kNN 圖，有系統性漏掉「精確公式本來就是設計來抓住」的那些離群配對的風險。 這不是一個順便提一下的假設性但書——這是一個真實、還沒被量測過的風險，要把這一節的修正真正做完， 需要照第 7 節的做法跑一次自己的 confirmatory 消融，把稀疏近似版本跟目前的精確全配對版本 直接比較過，才能被信任成可以直接替換上去的版本。同樣地，迭代特徵分解那個接近 O(n log n) 的表現，取決於圖的 spectral gap， 是稀疏譜分群文獻裡常見的典型情況經驗宣稱，不是最壞情況下的保證。

這兩個修正是互補的，不是二選一，而且有先後順序：先做向量化，因為它風險低（演算法、保證都不變）， 而且已經能補上大部分通往 MBS 規模的差距；再做 kNN 稀疏化，因為它才是真正拆掉漸進天花板、 而不只是把牆推遠的做法，但它改變了實際在計算什麼，在 MBS 規模下被信任之前，需要自己的 confirmatory 驗證。截至本文件為止，兩者都還沒實作。

§ 總結

已發表的單一特徵 CQI k-means 方法，能乾淨地擴充成一個候選聯集——CQI、資源成本、 以及成對精確效用 regret——由一個精確 DP 評分器統一起來，讓每一次擴充在決策層級上都可證明是安全的。 第三個候選，切換狀態感知，同樣透過完整的冪集消融測試過，但在量化基礎上被排除： 不論和哪個家族組合、不論在哪種 dispersion 或 load 條件下，它的貢獻都明顯小於另外兩者。 在真實物理層模擬上，confirmatory 測試顯示保留下來的兩家族方法嚴格優於單純 CQI； 資源成本家族在中度通道分散情境下領先，regret-graph 家族則在分散度與負載都吃緊時反超並持續拉開差距， 而且它的貢獻會隨著真實資料使用者規模擴大而持續增加。這個貢獻目前還不是「免費」的： 實際量測（而不是只看漸進複雜度的階數）顯示，家族三的候選產生才是這個方法真正的成本瓶頸， 而在 MBS 真正的目標規模——數百到數千個使用者——下，目前這個沒有向量化的實作， 在任何可用的重新分組節奏下都不可行（第 8 節）。這個架構本身提供的退路——拿掉家族三、 只保留兩個 O(n) 的家族——是今天就能用、代價已被精確量化的部署選項 （第 7 節）；要在不放棄這個機制的情況下補上這個差距，有一條具體、分階段的路徑——先向量化， 再做 kNN 稀疏化——已經在第 9 節寫清楚，兩個步驟目前都還沒做。
